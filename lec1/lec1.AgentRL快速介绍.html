LLM Advanced Learning · Chapter: Agentic Post-training

Agentic RL：
从“答题模型”到“行动模型”

Agentic RL 不是只换成 PPO / GRPO，而是把优化对象从一个答案扩展为一段可执行、可反馈、可验证的长程交互轨迹。

SFT 学会怎么行动；RL 学会哪些行动真的有效。

01 · What changed?

核心变化：从 single-turn answer 到 multi-turn trajectory

传统 RL / Reasoning RL

\[ x \rightarrow y \] \[ R = R(x,y) \]
  • 输入一个题目，模型输出一个答案。
  • reward 多数来自最终答案是否正确。
  • 适合数学、代码、选择题、短程推理。

Agentic RL

\[ x \rightarrow \tau=(a_1,o_1,a_2,o_2,\ldots,a_T,o_T,y) \] \[ R = R(x,\tau) \]
  • 模型要多轮行动：计划、调工具、读反馈、修正。
  • reward 不只看答案，也看工具、过程、效率、错误恢复。
  • 适合 coding agent、web agent、function calling、数据分析。
讲法：Agentic RL 的对象不是 response，而是 trajectory。2 / 11

每一步做两件事

  • 模型生成 token。
  • 如果生成 tool call，就执行工具并拿到 observation。

什么时候结束？

  • 达到 max steps。
  • 测试通过 / verifier 判定完成。
  • 模型输出 finish / final answer。
讲法：agentic loop 让模型进入“行动—反馈—再行动”的闭环。3 / 11
03 · Tool calling as action

Tool call 是模型 token stream 里的一种 action

<tools> search_web(query: string) run_python(code: string) </tools> <tool_call> {"name":"run_python", "arguments":{"code":"..."}} </tool_call> <tool_response> execution result / error message </tool_response>

教学重点

  • tool schema 告诉模型有哪些动作可选。
  • tool call 由模型生成，要合法、参数正确。
  • tool response 是环境反馈，不是模型要背诵的标签。
  • 模型要读懂 observation，再决定下一步。
不要把 tool use 理解成 prompt trick；它是把“动作空间”显式交给模型。
讲法：工具调用格式通常需要 SFT cold start，否则 RL 探索会很稀疏。4 / 11
04 · Formalization

Agentic RL = Multi-turn MDP

状态 State

\[ s_t=(c_t,e_t) \]
\(c_t\)：LLM-visible context，包括 instruction、history、tool calls、observations
\(e_t\)：external environment state，包括 files、database、browser、API state

动作 / 转移 / 奖励

\[ a_t \sim \pi_\theta(\cdot\mid s_t) \] \[ s_{t+1}=T(s_t,a_t,o_t) \] \[ \tau=(s_0,a_1,o_1,r_1,\ldots,s_T,r_T) \]
\[ \max_\theta\; \mathbb{E}_{\tau\sim\pi_\theta}\left[R(\tau)\right] -\beta\,D_{\mathrm{KL}}(\pi_\theta\|\pi_{\mathrm{ref}}) \]

文本动作

append tokens to context

工具动作

modify environment + return observation

奖励

outcome reward + process reward

讲法：区别在于 state 包含环境状态，transition 可能由工具执行决定。5 / 11

SFT：学会怎么行动

\[ \mathcal{L}_{\mathrm{SFT}} = -\sum_j m_j\log \pi_\theta(z_j\mid z_{\lt j}) \] \[ m_j=1:\;\text{assistant action / tool call / final answer} \] \[ m_j=0:\;\text{user / system / tool observation} \]

RL：学会哪些行动有效

\[ \tau_i\sim\pi_\theta(\cdot\mid x) \] \[ \begin{aligned} R_i={}&R_{\mathrm{final}}+\lambda_1R_{\mathrm{tool}}+\lambda_2R_{\mathrm{process}}\\ &-\lambda_3N_{\mathrm{call}}-\lambda_4R_{\mathrm{invalid}} \end{aligned} \]
讲法：SFT 是冷启动，不是终点；RL 才把环境反馈变成能力。6 / 11
06 · Reward checkers

Reward 怎么实现？本质是一组可执行 checker

\[ \begin{aligned} R(\tau)=&\;w_{out}R_{out}+\sum_{t=1}^{T}\left( w_fR_{format,t}+w_{tool}R_{tool,t}+w_{arg}R_{arg,t} +w_{exec}R_{exec,t}+w_{prog}R_{progress,t} \right) \\ &-\alpha N_{call}-\beta N_{invalid}-\gamma N_{timeout} \end{aligned} \]

Rformat

是否有合法的 <tool_call>、JSON 可解析、字段完整。

Rtool

工具名是否选对：search / run / edit / browser / API。

Rarg

参数名和值是否正确：日期、城市、id、文件路径、query。

Rexec

工具是否成功执行：无 schema error、runtime error、timeout。

Rout

最终答案 / 环境状态 / 测试结果是否正确。

Penalty

无效调用、死循环、过多调用、提前终止、污染环境。

最重要：不要把 reward 当成一个神秘模型，它通常就是 parse、execute、compare、test。
讲法：final reward 看完成没有；intermediate reward 看每一步有没有推进环境状态。7 / 11
07 · Concrete implementation

一个具体例子：工具调用 reward 如何打分

航班查询 agent

Task: 找东京到首尔下周五最便宜直飞航班 Gold tool: search_flights(origin, destination, date, direct_only) Reward: R_format = valid_xml_json(tool_call) R_tool = name == "search_flights" R_arg = F1(arg_names) + value_match(date/city/direct_only) R_exec = tool runs successfully R_out = final answer == cheapest direct flight

Coding agent

Task: 修复 repo 里的 bug Trajectory: read_file → edit_file → run_tests → fix_error → finish Reward: R_exec = command / edit succeeds R_progress = more tests pass than before R_out = (# passed tests) / (# all tests) Penalty = invalid edit, timeout, too many calls
\[ R_{eff}=\mathbf{1}[R_{out}=1]\cdot\frac{0.2}{1+\max(0,N_{call}-N_{min})} \]
调用次数惩罚要小心：最好只在任务完成后奖励“少而准”，否则模型会学会少调用但不完成任务。
更推荐比较 final state / tests，而不是强迫模型复现唯一工具路径。
讲法：同一个目标可能有多条有效路径；reward 应该鼓励完成任务，而不是锁死轨迹。8 / 11
08 · RL objective

算法可以是 GRPO / PPO，关键是 reward 作用在整条轨迹

GRPO 讲法

\[ A_i=\frac{R_i-\mathrm{mean}(R)}{\mathrm{std}(R)} \] \[ r_i=\frac{\pi_\theta(\tau_i\mid x)}{\pi_{\mathrm{old}}(\tau_i\mid x)} \] \[ \begin{aligned} \mathcal{L}_{\mathrm{GRPO}} =-\mathbb{E}\Big[\min(&r_iA_i,\\ &\operatorname{clip}(r_i,1-\epsilon,1+\epsilon)A_i)\Big] \end{aligned} \]

为什么 long-horizon 更难

  • trajectory 长，credit assignment 难。
  • 每条 rollout 长度不同，完成时间不同。
  • 工具错误、环境随机性会引入噪声。
  • 有些系统会用 PPO + critic 做 token-level advantage，提高稳定性。
不要把 Agentic RL 讲成“GRPO 的又一个应用”；它的难点在 trajectory、environment、reward 和 rollout infrastructure。
讲法：算法名字不是灵魂；可验证交互任务才是灵魂。9 / 11
09 · Data construction

数据构造：从 task seed 到可验证轨迹

Task seed用户目标、初始环境、约束、ground truth / verifier。
Tool schema定义可用动作：search、browser、shell、edit、API、ask user。
SFT trajectory专家轨迹或合成轨迹：何时调工具、参数、如何读反馈。
RL rollout模型自己探索 K 条轨迹，环境执行，verifier 打分。

讲法：好数据不是“漂亮答案”，而是“能被环境验证的行动历史”。10 / 11
10 · Take-away

Take-away

1. 优化对象变了

从 answer 变成 trajectory：工具、观察、修正、终止都进入训练对象。

2. 数据形态变了

SFT 需要 tool-calling 轨迹；RL 需要可执行环境和 verifier，而不是普通 QA 标注。

3. 工程系统变了

要支持并发 rollout、环境隔离、异步训练、on-policy 数据新鲜度控制。

Agentic RL 的本质：
让模型在可验证环境中，通过长程行动轨迹学习“如何完成任务”。
可复用模板：
\[ \text{Task}+\text{Tool Schema}+\text{Sandbox Env}+\text{SFT Trajectory}+\text{Verifier Reward}+\text{PPO/GRPO} \]
补一句：agentic post-training 不只是封装 agent，而是把 agent 行为拿来训练模型。11 / 11
